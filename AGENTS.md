# План агента: React Component Library + CI/CD

## Цель

Изучить основы GitLab CI и GitHub Actions, разработать небольшую библиотеку UI-компонентов и настроить полный CI/CD-процесс на GitHub Actions.

### Технологический стек

- TypeScript
- React
- Storybook
- CSS Modules
- Changesets
- Rollup
- Vitest
- Playwright — скриншотные тесты
- GitHub Actions
- GitHub Pages — публикация Storybook

## Этап 1. Изучение теории CI/CD

Изучить и кратко законспектировать:

1. Основы CI/CD: Continuous Integration, Continuous Delivery и Continuous Deployment.
2. GitLab CI:
   - `.gitlab-ci.yml`;
   - stages, jobs, scripts;
   - runners, artifacts, cache;
   - variables, rules, dependencies;
   - ручные и автоматические jobs.
3. GitHub Actions:
   - workflows, events, jobs, steps;
   - runners, actions, artifacts, cache;
   - secrets, permissions, environments;
   - `workflow_dispatch`, `push`, `pull_request`;
   - `needs`, матрицы, условия выполнения;
   - публикация пакетов и статических сайтов.
4. Сравнить GitLab CI и GitHub Actions: основные понятия, различия и сценарии применения.
5. Изучить версионирование библиотек по SemVer и релизный процесс с Changesets.

**Результат:** краткий конспект и схема CI/CD-процесса будущей библиотеки.

## Этап 2. Инициализация проекта

1. Проверить состояние репозитория и существующие соглашения.
2. Если проект уже существует — адаптировать его без необоснованного пересоздания конфигурации.
3. Если репозиторий пустой — создать проект с TypeScript и React.
4. Настроить пакетный менеджер и зафиксировать его версию через `packageManager`.
5. Настроить:
   - TypeScript;
   - ESLint;
   - форматирование кода;
   - CSS Modules;
   - Vitest;
   - Rollup;
   - Storybook;
   - Changesets;
   - Playwright.
6. Настроить единые команды в `package.json`.

**Результат:** проект устанавливается с нуля и готов к разработке.

## Этап 3. Реализация библиотеки компонентов

Реализовать минимум три компонента разной сложности, например:

- `Button` — варианты оформления, размеры, состояния disabled и loading;
- `Input` — controlled/uncontrolled сценарии, label, error;
- `Checkbox` — checked, disabled, обработчик изменения.

Требования:

1. Использовать React и TypeScript.
2. Стили хранить в CSS Modules.
3. Экспортировать компоненты через единый публичный API.
4. Описать типы публичных props.
5. Предусмотреть доступность: семантические элементы, ARIA только там, где необходимо, управление с клавиатуры.
6. Не раскрывать внутренние файлы и реализации в публичном API без необходимости.
7. Добавить README с примерами установки и использования.

**Результат:** рабочая библиотека с типизированным API и базовыми компонентами.

## Этап 4. Сборка через Rollup

1. Настроить Rollup для сборки библиотеки.
2. Формировать ESM и CJS-выходы, если они нужны целевым потребителям.
3. Генерировать декларации типов TypeScript (`.d.ts`).
4. Настроить обработку CSS Modules.
5. Исключить `react` и `react-dom` из bundle, объявив их корректными `peerDependencies`.
6. Настроить `exports`, `main`, `module`, `types` и `files` в `package.json`.
7. Проверить содержимое итогового пакета через `npm pack`.
8. Проверить импорт собранной библиотеки в небольшом тестовом потребителе.

**Результат:** библиотека собирается и может использоваться в другом React-проекте.

## Этап 5. Storybook

1. Настроить Storybook для React и TypeScript.
2. Создать stories для каждого компонента.
3. Покрыть основные варианты, состояния и граничные сценарии.
4. Добавить документацию по props и примеры использования.
5. Проверить локальную сборку Storybook.
6. Подготовить конфигурацию для публикации статической версии на GitHub Pages.

**Результат:** интерактивная документация компонентов.

## Этап 6. Unit- и интеграционные тесты

1. Настроить Vitest и подходящую среду тестирования React-компонентов.
2. Добавить Testing Library, если она нужна для проверки пользовательского поведения.
3. Покрыть тестами:
   - рендеринг;
   - props и варианты компонентов;
   - пользовательские события;
   - disabled и error-состояния;
   - граничные сценарии.
4. Добавить команды `test` и `test:coverage`.
5. Проверить, что тесты работают локально и завершаются с ненулевым кодом при ошибке.

**Результат:** автоматические тесты поведения компонентов.

## Этап 7. Скриншотные тесты на Playwright

1. Настроить Playwright для визуальных регрессионных тестов.
2. Выбрать источник тестовых страниц: отдельные тестовые примеры или запущенный Storybook.
3. Определить набор критичных stories для визуальной проверки.
4. Настроить единое окружение сравнения:
   - зафиксировать версию браузера и ОС в CI;
   - использовать одинаковые шрифты и зависимости;
   - отключить анимации и переходы;
   - дождаться загрузки шрифтов и завершения рендеринга;
   - фиксировать viewport, device scale factor и цветовую схему;
   - стабилизировать данные, время и случайные значения;
   - исключить нестабильные области через masking только при необходимости.
5. Запускать тесты в контейнере или окружении с одинаковыми браузерными зависимостями.
6. Хранить эталонные скриншоты в репозитории.
7. Настроить загрузку скриншотов, отчётов и trace в GitHub Actions при падении тестов.
8. Не обновлять эталоны автоматически в обычном CI. Обновление должно выполняться осознанно разработчиком.
9. Проверить стабильность повторными запусками на одном и том же коммите.
10. При выявлении flaky-тестов устранить причину, а не маскировать её увеличением допусков.

**Результат:** воспроизводимые визуальные тесты без случайных падений в CI.

## Этап 8. Changesets и стратегия релизов

1. Настроить Changesets для управления версиями и changelog.
2. Определить правила версионирования SemVer:
   - patch — исправления;
   - minor — новая обратносуместимая функциональность;
   - major — несовместимые изменения.
3. Настроить создание changeset при изменениях публичного API.
4. Выбрать схему beta-релизов: отдельный prerelease-режим Changesets с суффиксом, например `beta`.
5. Определить, куда публикуются релизы: npm либо другой явно заданный registry.
6. Разделить beta- и stable-релизы по триггерам, тегам/версиям и credentials.
7. Проверить, что beta-релиз не создаёт стабильную версию и не запускает стабильную публикацию повторно.

**Результат:** предсказуемое версионирование и управляемый выпуск релизов.

## Этап 9. GitHub Actions — CI для Pull Request

Создать workflow, который запускается на `pull_request` в основную ветку.

Стадии:

1. **Install** — установка зависимостей по lock-файлу.
2. **Lint** — ESLint и проверки форматирования, если они включены.
3. **Typecheck** — проверка типов TypeScript.
4. **Build** — сборка библиотеки и Storybook.
5. **Unit tests** — запуск Vitest.
6. **Visual tests** — запуск Playwright screenshot-тестов.

Требования:

- jobs должны иметь корректные зависимости через `needs`;
- независимые проверки запускать параллельно, где это оправдано;
- использовать кэш зависимостей;
- ограничить `permissions` минимально необходимыми;
- не запускать публикацию пакета и деплой Storybook на обычном PR;
- сохранять диагностические артефакты при падении тестов;
- настроить обязательные status checks для merge.

**Результат:** PR нельзя смержить при неуспешной проверке обязательных стадий.

## Этап 10. Ручной beta-релиз

Создать отдельный workflow с запуском через `workflow_dispatch`.

Последовательность:

1. Проверить состояние ветки и доступность изменений для релиза.
2. Установить зависимости.
3. Запустить lint, typecheck, unit- и визуальные тесты.
4. Собрать библиотеку.
5. Включить prerelease-режим Changesets с идентификатором `beta`.
6. Сформировать beta-версии и changelog.
7. Опубликовать beta-версию в выбранный registry с соответствующим тегом.
8. Сохранить отчёт о релизе.

Условия безопасности:

- stable-релиз не должен запускаться из beta-workflow;
- повторный запуск должен корректно обрабатывать уже опубликованные версии;
- публикация должна использовать отдельные минимально необходимые права и secrets;
- при необходимости предусмотреть выбор beta-идентификатора или параметров релиза вручную.

**Результат:** beta можно выпустить вручную без публикации stable-версии.

## Этап 11. Stable-релиз после merge

Создать workflow, который запускается при `push` в основную ветку после merge.

Последовательность:

1. Установить зависимости.
2. Проверить lint, TypeScript, unit-тесты и визуальные тесты.
3. Собрать библиотеку.
4. Проверить наличие готовых changesets.
5. Выполнить автоматизированный релизный процесс:
   - определить следующую версию;
   - обновить версии пакета;
   - сформировать changelog;
   - создать release PR либо использовать согласованный автоматический механизм релиза;
   - после утверждения и merge релизного PR опубликовать stable-версию.
6. Создать GitHub Release и/или тег, если это предусмотрено выбранной схемой.
7. Не публиковать пакет повторно, если версия уже существует.

Важно: обычный merge в основную ветку не всегда должен напрямую публиковать новую версию. При использовании стандартного Changesets flow merge сначала может обновить версии и changelog в release PR. Нужно выбрать одну последовательную схему и исключить циклические запуски workflow.

**Результат:** стабильные релизы проходят контролируемый и воспроизводимый процесс.

## Этап 12. Автоматическая публикация Storybook

Настроить отдельный workflow на `push` в основную ветку.

1. Установить зависимости.
2. Собрать Storybook в статические файлы.
3. Опубликовать артефакт на GitHub Pages через официальный механизм GitHub Actions.
4. Настроить Pages в настройках репозитория.
5. Выдать workflow только необходимые `permissions`.
6. Проверить, что сайт доступен после успешного деплоя.
7. Убедиться, что деплой Storybook не зависит от публикации npm-пакета, если это не требуется.

**Результат:** после merge в основную ветку документация обновляется автоматически.

## Этап 13. Финальная проверка и документация

1. Проверить все команды локально.
2. Проверить workflow на PR.
3. Проверить ручной beta-релиз.
4. Проверить stable-релиз на тестовом сценарии без публикации дублирующей версии.
5. Проверить деплой Storybook.
6. Проверить, что скриншотные тесты стабильны при повторных запусках.
7. Документировать:
   - архитектуру проекта;
   - локальный запуск;
   - добавление компонента;
   - написание unit- и visual-тестов;
   - добавление changeset;
   - выпуск beta;
   - выпуск stable;
   - настройку secrets и GitHub Pages.

## Критерии готовности

- [ ] Библиотека содержит минимум три типизированных React-компонента.
- [ ] Работает сборка Rollup и генерируются типы.
- [ ] Storybook описывает все компоненты.
- [ ] Vitest покрывает ключевое поведение компонентов.
- [ ] Playwright выполняет визуальные проверки стабильно.
- [ ] PR workflow проверяет код, сборку и тесты.
- [ ] Beta-релиз запускается вручную.
- [ ] Stable-релиз проходит согласованный Changesets-процесс.
- [ ] Storybook автоматически публикуется после merge в основную ветку.
- [ ] Секреты не хранятся в репозитории.
- [ ] README описывает разработку и релизный процесс.

## Правила работы агента

1. Перед началом изучить репозиторий, package manager, структуру, ветки и существующие конфигурации.
2. Сначала составить короткий технический план и перечень решений, требующих выбора.
3. Не выполнять масштабные изменения без необходимости и не заменять существующие инструменты без обоснования.
4. После каждого этапа запускать релевантные проверки и фиксировать результат.
5. Не считать этап завершённым, пока его критерии готовности не выполнены.
6. Не публиковать реальные пакеты и не изменять настройки репозитория без подтверждённых credentials и необходимых разрешений.
7. Если для продолжения требуется решение пользователя — описать варианты и их последствия, затем запросить выбор.
8. В финале предоставить список реализованного, команды запуска, структуру workflows и известные ограничения.
